# Weave Knowledge Graph

> 将长文本拆解为结构化知识网络，支持演化追踪和语义查询。

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

---

## 一句话

**Weave 是 AI Agent 技能文件（SKILL.md）+ Python 工具。** 给 AI Agent 装上知识图谱能力——接收文章、视频字幕、对话记录，自动完成**内容切割 → 命题/对话/事件提取 → 标签索引 → 向量化 → 演化追踪 → 语义查询**。

> 运行需要：① AI Agent 环境（Claude Code、Cursor、Trae 等）；② LLM API（入库管道依赖）；③ Python 3.10+（向量化、查询）。
>
> 作者开发环境为 Trae，其他平台可能存在少量适配差异。

---

## 现有工具的痛点

学术界和工业界已经积累了大量关于知识管理、知识图谱、检索增强的研究成果。但现有工具各有一块硬伤：

| 工具 | 核心痛点 | 理想解法 |
|------|----------|---------|
| **Obsidian / Notion** | 手动打标签，无法跨文档发现矛盾和共识。条目越多，线性搜索越慢 | 知识图谱 + 向量索引 |
| **LLM Wiki** | LLM 隐式推断关系，来源不可追溯。每次查询烧 token。增量更新需重建全图 | 命题存证 + 向量检索 |
| **传统 RAG** | 固定大小切 chunk——一句话被拦腰截断。chunk 内信息混杂，细节被淹没。没有知识演化 | 语义边界切割 + 原子命题向量化 |
| **传统 KG** | 二选一（少数派直接消失）、人工标注（覆盖不到小众内容）、版本快照（看不到演化历史） | 共识簇 + 少数派保护 + 演化追踪 |

**Weave 做的事情**：把学术界和工业界已经探索过的方向落地成一个可运行的工程系统。

**关于知识真实性**：Weave 不宣称自己"知道真相"。

1. **原子化拆分**：原文被拆成 2515 条独立命题，每条命题独立存储、独立检索——不会因为某个观点出现频率高而淹没低频观点。少数派同理被保留。
2. **LLM 初步处理**：得益于 LLM 长上下文能力的提升，当前主流模型 200K 高质量上下文窗口足以容纳查询返回的命题集合。原子化后的命题结构紧凑，实际输出量远低于上下文上限，不存在注意力衰减问题。LLM 可对这些命题进行合并、分类、输出初步评价。
3. **人最终裁定**：LLM 的建议只是参考，最终判断权在人。
4. **原文追溯**：每个命题带 `source_id`（BV 号、书号等唯一标识）+ `title` + `author` + `date` + `original_text`，任何结论都可追溯到原始段落。
5. **脚本入库**：LLM 直接输出 JSON 容易出现格式错误（漏逗号、引号未转义），导致搜索失败。项目已用 Python 脚本接管入库环节，对 LLM 输出做格式校验和修复后再写入，避免静默失败。

**已知局限**：当相同观点在多个来源中重复出现时，尚未做同类项合并的架构设计——当前 2515 条命题中存在冗余表述，这是下一步优化方向。

## 对比

每个对比只讲两件事：**他们的痛点 → 我们怎么解决**。实测数据见下方 §实测性能。

### vs Obsidian / Notion

| 痛点 | Weave 解法 |
|------|-----------|
| 手动打标签，几百篇笔记后找不到东西 | AI 自动按段落分类，标签+向量双路召回 |
| 两个作者说矛盾的话，全靠人眼对比 | Evolution-Tracker 标记候选矛盾，人工审核确认 |
| 新增内容后旧知识是否过时，不知道 | 新命题入库 → 自动匹配共识簇 → 标记新增/重合/潜在矛盾 |

### vs LLM Wiki

| 痛点 | Weave 解法 |
|------|-----------|
| LLM 推断的关系，来源不可追溯 | 每个命题带 `original_text` + BV号，可回溯到原文段落 |
| 每次查询都烧 token | 向量检索，查询时无 LLM 调用 |
| 新增内容需重建整个图谱 | 增量入库，新命题直接接入 |

### vs 传统 RAG

RAG 的五个结构性问题，不是工程实现问题，是架构层面就注定的：

| # | RAG 的痛点 | Weave 的解法 |
|:--:|-----------|-------------|
| 1 | **生硬切割**：固定 token 大小切 chunk，一句话被拦腰截断 | 按语义边界切——话题转换处才是切割点。LLM 根据内容类型（论证/对话/教学等）判断段落边界 |
| 2 | **整段向量匹配**：一个 chunk 生成一个向量，但 chunk 内信息混杂，什么都像、什么都不准 | 每个命题单独向量化，一个 500 字段落拆成 5-10 个命题，每个有精确语义向量 |
| 3 | **细节淹没**：核心观点藏在段落里，向量匹配时信号被稀释 | 命题化把核心观点单独提取，SRO 三元组独立存储、独立检索 |
| 4 | **无知识演化**：新文档加进来只是多了几个 chunk，不会告诉你旧知识过时了 | Evolution-Tracker 标记候选矛盾，共识簇跟踪知识演化 |
| 5 | **原文无结构**：chunk 是裸文本片段，没有标注这是"观点"还是"案例" | 命题带 SRO 结构标注 + `original_text`，segment_id 保留段落关联，支持向上追溯到原始段落 |

### vs 传统知识图谱

| 痛点 | Weave 解法 |
|------|-----------|
| 二选一，少数派观点直接消失 | 两方都保留，标记为讨论层，少数派信号受保护 |
| 人工标注，覆盖不到小众内容 | AI 自动从文本提取，按需消费各类内容（当前已在中文视频字幕上验证） |
| 版本快照，看不到"何时从 A 变为 B" | 演化历史可追溯，共识簇带时间线 |
| 二元真/假，没有置信度 | 每个命题有 confidence + 来源，可回溯验证 |

## 少数派保护

自媒体时代的核心问题不是"信息过载"，而是**信号同质化**：

```
热点出现 → 大量创作者跟进 → 观点同质化 → 算法推荐 → 更多同质内容
                                                              ↓
                                                真实的、本质的观点被信号淹没
```

传统知识系统对信号偏差没有免疫力——它们按"出现频率"赋予权重，同质化内容天然占优。

Weave 的四种保护机制：

| 机制 | 做法 |
|------|------|
| 不按频率加权 | 100 个来源重复 ≠ 比唯一来源更"正确" |
| 少数派信号标记 | 与主流簇不匹配的命题标记 `minority_signal`，保留待验证 |
| 讨论层而非综合 | 矛盾不抹平，两方观点平行展示 |
| 演化追溯 | 过去的少数派后来被验证正确时，演化历史可追溯 |

## 实测性能

> 数据来源：B站博主 **@唯一讲述者** 的 304 个公开视频，经 OCR 提取字幕，AI Agent 管道处理。以下以查询"什么是言权倒置"为例，展示完整管道每一步的耗时和返回内容。

**环境**：2515 条命题，BGE-M3 嵌入 1024 维，FAISS IndexFlatIP，SiliconFlow API

### 1. 嵌入 — 620ms

查询文本 `"什么是言权倒置"`（7 字）→ BGE-M3 编码为 1024 维归一化向量。耗时 620ms，瓶颈在网络 API。

### 2. FAISS 向量检索 — 1.5ms

在 2515 个向量中搜索 Top-100。耗时 1.5ms，本地完成。

命中结果按相似度排序：

| 排名 | 相似度 | SRO 命题 |
|:--:|:--:|------|
| 1 | 0.8071 | 言权倒置 \| 定义 \| 现实弱势方在舆论场强势 |
| 2 | 0.7579 | 言权倒置 \| 描述 \| 现实弱势者在舆论上天然强势 |
| 3 | 0.7453 | 言权倒置 \| 指 \| 现实越强势舆论越弱势的规律 |
| 4 | 0.7364 | 言权倒置（讲述者提出的公关概念）\| 指 \| 现实生活中越弱势的群体，在舆论场上就越强势 |
| 5 | 0.7117 | 言权倒置 \| is \| 社会权力与舆论话语权成反比 |

相似度分布：min=0.4277, max=0.8071, avg=0.4727, top-5 全部 > 0.7。

### 3. id_map 反查 — 0.1ms

100 个 FAISS 索引 → 命题 ID 映射。去重后 80 个唯一来源视频。

### 4. 动态池裁剪 — 12 条送重排序

阈值 0.5 裁剪：12 条相似度 ≥ 0.5，送 BGE-Reranker-v2-M3 精排。88 条低于阈值被截断。

### 5. 重排序 — 600ms

12 条 SRO 文本 → BGE-Reranker-v2-M3 重打分。8/10 排名发生变动：

| 排名变动 | 重排序得分 | SRO 命题 |
|:--:|:--:|------|
| #4→#1 ↑ | 0.9977 | 言权倒置（讲述者提出的公关概念）\| 指 \| 现实生活中越弱势的群体，在舆论场上就越强势 |
| #3→#2 ↑ | 0.9975 | 言权倒置 \| 指 \| 现实越强势舆论越弱势的规律 |
| #2→#3 ↓ | 0.9968 | 言权倒置 \| 描述 \| 现实弱势者在舆论上天然强势 |
| #1→#4 ↓ | 0.9956 | 言权倒置 \| 定义 \| 现实弱势方在舆论场强势 |
| #5→#5 — | 0.9936 | 言权倒置 \| is \| 社会权力与舆论话语权成反比 |

重排序得分分布：min=0.7461, max=0.9977, avg=0.9410。FAISS 相似度最高的 #1 被重排序推到 #4——FAISS 侧重关键词匹配，Reranker 侧重语义质量。

### 6. 文本富化 — 70ms

Top-10 命题加载完整原文（`original_text`）、标题、作者、日期，返回最终结果。

### 汇总

| 阶段 | 耗时 | 类型 |
|------|:--:|------|
| 1. 嵌入 | 620ms | 🌐 API |
| 2. FAISS 检索 | 1.5ms | ✅ 本地 |
| 3. id_map 反查 | 0.1ms | ✅ 本地 |
| 4. 动态池裁剪 | <1ms | ✅ 本地 |
| 5. 重排序 | 600ms | 🌐 API |
| 6. 文本富化 | 70ms | ✅ 本地 |
| **总计** | **725ms** (无 Rerank) / **1160ms** (带 Rerank) | |

**瓶颈 100% 在网络 API**。本地部分（FAISS + id_map + 富化）合计 < 2ms。

### 理论改善空间

| 指标 | 当前 | 换本地模型 | 改善 |
|------|:--:|:--:|:--:|
| 嵌入 | 550-620ms | ~10ms (BGE-M3 本地) | **55x** |
| 重排序 | 600ms | ~10ms (BGE-Reranker 本地) | **60x** |
| FAISS | 0.5-1.5ms | 已最优 | — |
| **总计** | **725ms** | **~20ms** | **36x** |

### vs Obsidian（缩放趋势对比）

Obsidian 的搜索是逐文件线性扫描——文件翻倍，搜索时间翻倍。Weave 的 FAISS 索引是预构建向量矩阵，检索时间与文件数解耦。

| 文件量 | Obsidian（关键词搜索） | Weave FAISS（语义搜索） |
|------|------|------|
| 304 文件 | 秒级（首次 ~5-15s，缓存后 <1s） | 1.5ms |
| 1,000 文件 | 秒级，线性增长 | ~6ms |
| 10,000 文件 | 十秒级，线性增长 | ~60ms |
| 100,000 文件 | 分钟级，不堪用 | ~10ms (IndexIVFFlat) |

> 核心差异不在绝对速度，而在**缩放曲线**：Obsidian 文件翻倍 → 搜索时间翻倍；Weave 文件翻倍 → FAISS 检索时间几乎不变。Obsidian 数字为保守估算（含磁盘 I/O），Weave 数字仅 FAISS 向量检索阶段。

### vs LLM Wiki（实测估算）

LLM Wiki 的查询通常需要 LLM 读取图谱结构——数据量越大，上下文越长，token 消耗和延迟随之增长。Weave 的 FAISS 检索不经过 LLM，查询成本与数据量无关。

| 数据量 | LLM Wiki 估算 | Weave FAISS | 差距 |
|------|:--:|:--:|:--:|
| 2,515 命题 | ~10-20s, ~$0.03/次 | **1.5ms**, $0/次 | **7,000x** (延迟) |
| 10,000 命题 | ~30-60s, ~$0.10/次 | ~6ms, $0/次 | **10,000x** |
| 100,000 命题 | 超出上下文窗口，需分块策略 | ~10ms, $0/次 | **不可比** |

> 估算依据：LLM Wiki 查询需将图谱序列化后送入 LLM 上下文，按 2,515 命题约 50K tokens（DeepSeek 输入 $0.27/1M tokens ≈ $0.014/次）。实际开销因实现方式而异。Weave 查询端完全不调用 LLM，仅 FAISS 向量匹配。

**但 LLM Wiki 有 Weave 做不到的事**：交互式可视化浏览、无需预设问题即可探索概念关联。两者互补：LLM Wiki 适合"随便逛逛"，Weave 适合"精准查找"。

## 模型选择

入库管道中不同步骤对模型能力要求不同。基于 V4 Pro vs Flash 实测对比：

| 维度 | Pro | Flash | 差距 |
|------|:--:|:--:|:--:|
| 命题数 | ✅ | ⚠️ | Flash 少 30-47% |
| 命题格式 | 完整（speaker+evidence+confidence） | 结构化（因果链链接） | Flash 并段丢角度 |
| 叙事识别 | ✅ | ❌ | Flash 完全零识别 |
| 教学单元 | ✅ | ⚠️ | 差距 25% |
| Q&A 提取 | ✅ | ✅ | 完全等价 |

**建议**：

| 内容类型 | 推荐 | 原因 |
|------|:--:|------|
| 对话/访谈 | **Pro** | 隐喻、多人、叙事交织，Flash 差 47% |
| 论证/观点 | **Pro** | Flash 并段丢角度 |
| 教学/教程 | Flash 可 | 差距仅 25% |
| 仅 Q&A | Flash 可 | 完全等价 |

> 入库是**一次性成本**，知识图谱要用很久。垃圾进，垃圾出。

## 快速开始

### 前置条件

- AI Agent 环境（Claude Code、Cursor、Trae 等。作者使用 Trae，其他平台可能有少量适配差异）
- LLM API（DeepSeek V4、Claude 等）
- Python 3.10+
- 嵌入 API（SiliconFlow BGE-M3、OpenAI text-embedding-3 等）

### 安装

```bash
pip install -r scripts/requirements.txt
```

### 配置

```bash
export EMBED_API_KEY="your-api-key"
export EMBED_API_BASE="https://api.siliconflow.cn/v1"
export EMBED_MODEL="BAAI/bge-m3"
export KG_SHARED_DIR="./examples/real-kg-data/_shared"
```

### 运行

```bash
# 语义查询
python scripts/query.py "什么是言权倒置" --kg-dir examples/real-kg-data

# 带重排序
python scripts/query.py "危机公关" --kg-dir examples/real-kg-data --rerank

# 查看详细日志
python scripts/query.py "品牌翻车" --kg-dir examples/real-kg-data --verbose
```

### 导入 Skill

`skills/` 目录下的 `SKILL.md` 文件可直接导入到 AI Agent 中使用。本质上是结构化的 Agent Prompt，也可提取纯文本作为 System Prompt。
